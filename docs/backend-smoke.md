# Backend smoke-test — 23 сентября 2026

## Запуск

Используется фактическая версия из lockfile: Prisma Client/CLI **5.22.0**, Node **24.19.0**, pnpm **10.16.1**. Переход на Prisma 7 не выполнялся.

```sh
corepack pnpm install
corepack pnpm prisma:generate
corepack pnpm prisma:migrate
corepack pnpm prisma:seed
corepack pnpm dev:api
```

В другом терминале, после ответа 200 от `http://localhost:4000/api/v1/health`:

```sh
corepack pnpm --filter @hackalem/api smoke
corepack pnpm typecheck
corepack pnpm build
corepack pnpm --filter @hackalem/api exec prisma validate
```

Если Node не виден в текущем PowerShell, обновить PATH для этой сессии:

```powershell
$env:Path = 'C:\Program Files\nodejs;' + $env:Path
```

Smoke запускается против локального API и общей с ним файловой системы. Можно задать `SMOKE_API_URL`. Для проверки fallback AI worker должен быть недоступен. Скрипт ищет seed по `audioUrl = seed://meeting-1.mp3`, временно меняет поручение и восстанавливает его в `finally`. Каждый запуск оставляет три отдельные встречи `Smoke …`, файлы live и записи экспорта для осмотра. Не запускать против рабочей базы: скрипт выполняет реальные записи. Повторный seed также создаёт новую демо-встречу.

## Результаты

- Установлены зависимости, сгенерирован Prisma Client, создана и применена миграция `20260923093220_init`, выполнен seed.
- Health, meetings list/get, transcript, topics, summaries (общие и по теме), tasks (общие и по теме): 200, ответы проверяются Zod-схемами contracts.
- PATCH поручения: описание, статус, срок и текст ответственного сохраняются; последующий GET возвращает изменения. Исходное поручение восстановлено. Некорректный статус возвращает ApiError/400, отсутствующая встреча — ApiError/404.
- Создание встречи, attach-audio, PATCH участника, stop-live: успешны.
- POST process при недоступном worker: `{ accepted: true, mode: "demo-fallback" }`, итоговый статус READY. Проверены duration, реплики, темы, саммари, поручения и ссылки на участников/реплики/темы.
- Отдельно отправлен demo-result через HTTP webhook: READY и те же тексты реплик. Оба пути используют `handleResult → saveProcessingResult`.
- WS принимает два бинарных чанка (6 и 131072 байта). После disconnect: UPLOADED, заполнен audioUrl, файл побайтово равен объединённым чанкам. Это тест транспорта, байты не являются воспроизводимой аудиозаписью.
- DOCX export/download: 201/200, ZIP-сигнатура и имя файла корректны. Копия: `apps/api/storage/smoke/seed-protocol.docx` (игнорируется Git).
- XML DOCX прочитан: заголовок, организация, дата, две тематические части, спикеры с ролями, реплики в соответствующих частях, таблица «Поручение / Ответственный / Срок», саммари первой темы. У второй темы seed не содержит поручений/саммари, общего саммари в seed также нет.
- В исходном прогоне PDF-запрос при отсутствии `soffice` возвращал DOCX. Это поведение заменено прямой генерацией PDF; результат повторного прогона ниже.
- `pnpm typecheck`, полный `pnpm build` (API + web), `prisma validate` прошли. После последних изменений backend повторно собран и проверен.

## Исправлено

- Методный Zod-pipe применял body-схему к `:id`, вызывая 400 на корректных PATCH/POST. Теперь проверяется только body.
- Swagger генерируется после установки глобального prefix: операции используют `/api/v1`, интерфейс остаётся на `/api/docs`.
- Download экспорта разрешает путь файла в абсолютный путь.
- Live выставляет UPLOADED после завершения записи буферизованных чанков.
- Экспорт теперь создаёт PDF напрямую и сообщает фактический формат.

## Повторный прогон на реальном MP3

- Добавлен `POST /api/v1/meetings/:id/upload` с multipart-полем `file`: до 50 МиБ, непустой MP3 с проверкой расширения и заголовка. Smoke загружает `ml/data/private/meeting_01.mp3` в новую FILE-встречу и сверяет сохранённый файл побайтово. `attach-audio` остаётся для уже доступного серверу пути/URL.
- `process` на встрече в PROCESSING/READY отвечает 409. Повторный webhook не создаёт дубли: переход статуса и запись результата выполняются в одной транзакции. Это семантика «одна успешная обработка»; редактирование поручений после READY сохраняется. Повторная обработка с заменой результата пока не предусмотрена.
- Live проверяет существование и статус встречи, отклоняет второе одновременное соединение и текстовые сообщения, не финализирует пустую или неудачную запись. После закрытия записи smoke сверяет байты и статус UPLOADED. Частичного live-транскрипта пока нет.
- PDF теперь генерируется backend напрямую через pdfmake без `soffice`. Smoke проверяет формат скачанного файла. Дополнительно PDF seed-встречи отрендерен локально: одна страница, кириллица извлекается, темы и таблица поручений видны без обрезки. Копия: `apps/api/storage/smoke/seed-protocol.pdf` (игнорируется Git).

## Непроверенное и ограничения

- Визуальная проверка **DOCX** и точное сравнение с эталонным DOCX ещё не завершены. XML подтверждает содержимое, но не вёрстку; ранее доступ к Word через Computer Use был отклонён. Эталонные DOCX теперь есть только в игнорируемой приватной ML-папке.
- Реальный AI worker с обратным webhook ещё не прогнан. Два настоящих MP3 уже локально транскрибированы (`docs/ml-audio-smoke.md`), но backend smoke по-прежнему проверяет `demo-fallback` после загрузки MP3. До реального прогона нужно обеспечить чтение `audioUrl` worker-процессом и доступность `callbackUrl` из него.
- Для полной диаризации требуется доступ к весам Community-1; пользователь сообщил, что доступа пока нет. Локальная Ollama и модель для извлечения поручений устанавливаются отдельно. Результат fallback нельзя выдавать за анализ загруженного MP3.
- Успешная повторная обработка с заменой старого результата и частичная live-транскрипция не реализованы. Текущая семантика защищает ручные правки от дублей.

Следующий практический прогон: локальный AI worker → MP3 из `upload` → реальный `process` → webhook → READY → проверка поручений и их ручная правка → DOCX/PDF, визуальная сверка с эталоном.
